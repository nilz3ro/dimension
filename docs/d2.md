# Dimension V2: LLM-Aware Orchestration Layer

Future evolution where Dimension moves from being a stateful agent runtime to
an **LLM-aware middleware** that owns the orchestration loop.

## The Shift

In V1, the agent is a self-contained program inside the VM. It calls the LLM,
interprets tool calls, executes them, and loops — Dimension just provides
the stateful environment (filesystem, session, context).

In V2, Dimension itself becomes the orchestration loop:

```
Message In
  → Route to LLM provider     ─┐  (parallel)
  → Spin up VM(s)              ─┘
  ← LLM responds with tool calls
  → Dispatch tool calls to VM(s) (fan-out, VMs are cheap)
  → Collect results
  → Feed back to LLM
  → ... loop until final response
  → Persist state
  → VM teardown
```

The VM becomes a pure **tool execution sandbox** rather than an agent host.

## Why This Might Be a Separate Project

- Fundamentally different responsibility model — Dimension goes from
  "provide environment, forward messages" to "drive the entire agentic loop"
- Requires an LLM router with provider abstractions (Anthropic, OpenAI, local)
- Requires parsing and understanding tool call schemas, not just opaque JSON
- New wire protocol: instead of forwarding a full request, Dimension sends
  targeted `ToolCallRequest` messages and receives `ToolCallResult` responses
- Changes the trust model — the agent no longer decides what LLM calls to make

## What It Enables

- **Parallel tool execution** across multiple VMs simultaneously
- **Latency optimization** — LLM call starts before any VM is ready
- **Policy enforcement** — Dimension can inspect/block/modify tool calls
- **Visibility** — full observability into the agent's reasoning and actions
- **Cost control** — Dimension tracks token usage, can enforce budgets
- **Provider routing** — use different models for different parts of a task
- **Streaming tool calls** — start executing tool calls as they stream in
  from the LLM, don't wait for the full response

## Key Components (not in V1)

- **LLM Router**: provider abstraction, streaming completions, tool call parsing
- **Tool Execution Protocol**: structured request/result messages over vsock
- **VM Pool**: warm VMs ready for instant tool execution
- **Tool Registry**: what tools are available, their schemas, resource requirements
- **Orchestration Loop**: the LLM ↔ tool call cycle, managed by Dimension
- **Result Merging**: combining outputs from parallel tool executions

## Open Questions

- Could this be a layer on top of V1 rather than a replacement? i.e., V1's
  "full agent in a VM" mode coexists with V2's "tool sandbox" mode
- How does the agent's internal state work when it doesn't own the loop?
  Some agents need memory between tool calls that isn't just filesystem state
- Is this actually a different product? V1 = "run agents", V2 = "be an agent"
